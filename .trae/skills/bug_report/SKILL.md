# Bug 报告生成

在完成一次 Bug 定位与修复（或用户明确要求记录某次缺陷处理）后，将完整过程整理成 Markdown 报告，写入项目的 `.lqs/bug_report/` 目录，方便日后追溯与复用。

## 使用时机

- 用户说"把这次 bug 修复写成报告"、"记录一下这个问题"、"沉淀修复日志"、"存档"；
- 你刚完成一个 Bug 的定位与修复，且问题具有可复现性、值得留档；
- 用户要求创建/更新 bug 修复报告。

## 报告文件命名

文件名格式：`<序号>_<时间戳>_<摘要>.md`

- **序号**：三位数字，按 `.lqs/bug_report/` 目录中已有报告递增（无则从 `001` 开始）。
- **时间戳**：`YYYYMMDD_HHmmss`（本地时间，用 `Get-Date -Format "yyyyMMdd_HHmmss"` 获取）。
- **摘要**：8~20 字，概括问题现象（避免过长，不含 `/\:*?"<>|`）。

示例：

```
001_20260809_161809_模型清单展示异常与算法注册500修复.md
002_20260810_093012_计数热力图索引越界修复.md
```

## 报告结构

生成的报告需包含以下小节，内容务必**基于实际排查证据**（运行日志、报错栈、接口返回），禁止编造：

```markdown
# Bug 修复报告 #<序号>

- **报告编号**：<序号>
- **记录时间**：<时间戳>
- **问题标题**：<一句话概括>
- **涉及模块**：<涉及的文件/模块>
- **严重程度**：<高/中/低>
- **状态**：已修复并验证

---

## 一、问题现象
<用户可感知的表现，尽量还原现场>

## 二、排查过程
### 2.x <步骤>
<数据流梳理 / 实际复现 / 根因定位，附关键日志与报错栈>

## 三、解决方案
<针对每个根因的修复，给出代码/配置改动要点>

## 四、验证结果
<表格列出：降级环境验证、完整环境验证、测试套件通过数>
<若清理了残留进程/端口，也在此记录>

## 五、经验教训
<可沉淀的通用结论，供后续同类问题参考>

## 六、修复文件清单
| 文件 | 改动 |
|------|------|
| <路径> | <改动说明> |
```

## 关键约束

1. **证据导向**：所有结论（根因、修复、验证）必须来自真实的文件内容、运行日志或接口响应，不要臆测。
2. **区分环境**：若存在多个 Python/Node 环境，务必记录验证所用环境，避免误导（例如本机 `uav-vis` 有 cv2、Anaconda base 缺失 cv2）。
3. **不重复造文件**：写报告前先 `LS .lqs/bug_report/` 确认是否已有同主题报告；若已有则考虑更新或新增。
4. **语言**：报告正文与用户沟通语言一致（默认中文）。

## 步骤

1. `LS` 查看 `.lqs/bug_report/` 现有文件，确定下一个序号。
2. 用 `Get-Date -Format "yyyyMMdd_HHmmss"` 取当前时间戳。
3. 按上述结构与命名规则，用 `Write` 创建报告文件。
4. 向用户确认文件已生成，并简述序号/标题。
