# 功能更新报告生成

在完成一次功能开发、模块优化或需求迭代（或用户明确要求记录某次更新）后，将完整过程整理成 Markdown 报告，写入项目的 `.lqs/update_report/` 目录，方便日后追溯、版本归档与经验沉淀。

## 使用时机

- 用户说"把这次更新写成报告"、"记录一下这个功能"、"沉淀开发日志"、"存档"、"写功能更新报告"；
- 你刚完成一个功能模块的开发/优化，且改动涉及前后端多个文件、具有留档价值；
- 用户要求创建/更新功能更新报告；
- 一个开发任务（plan）执行完毕并通过验证后，主动引导用户是否需要沉淀更新报告。

## 报告文件命名

文件名格式：`<序号>_<日期>_<摘要>.md`

- **序号**：三位数字，按 `.lqs/update_report/` 目录中已有报告递增（无则从 `001` 开始）。
- **日期**：`YYYYMMDD`（本地时间，用 `Get-Date -Format "yyyyMMdd"` 获取；时间戳部分可简化为 `_000000`，或使用精确时间 `yyyyMMdd_HHmmss`）。
- **摘要**：10~30 字，概括更新主题（避免过长，不含 `/\:*?"<>|` 等文件名字符）。

示例：

```
001_20260810_000000_算法管理模块优化FP16清理注册持久化文件上传图标统一.md
002_20260811_143022_数据集管理模块新增批量导入与标签校验功能.md
```

## 报告结构

生成的报告需包含以下小节，内容务必**基于实际开发过程与代码改动**，禁止编造未实施的内容：

```markdown
# 功能更新报告 #<序号>

- **报告编号**：<序号>
- **记录时间**：<YYYY-MM-DD 或 YYYYMMDD_HHmmss>
- **更新标题**：<一句话概括本次更新主题>
- **涉及模块**：<涉及的主要文件/模块路径>
- **更新类型**：<功能新增 / 功能增强 / 无用代码清理 / UI优化 / 重构 / 性能优化 等>
- **状态**：已完成并验证

---

## 一、需求背景
<为什么要做这次更新：用户提出的需求点、遗留问题、优化动机，逐条列出原始需求>

## 二、方案设计
### 2.x <子方案标题>
<针对每个需求点的技术方案设计：数据流、架构决策、交互设计、接口改动等>

## 三、改动详情
### 3.1 <配置层/后端/前端/...>
<分模块详细描述改动内容，包含关键代码片段、文件路径引用（使用 file:/// 绝对路径链接）>

## 四、验证结果
<表格列出：构建验证、功能测试、脚本测试、边界情况验证等，明确标注"通过/待实测/失败">
<若有临时测试脚本、清理操作，也在此记录>

## 五、经验总结
<可沉淀的通用结论、踩坑记录、最佳实践，供后续同类开发参考>

## 六、改动文件清单
| 文件 | 改动类型 | 改动摘要 |
|------|----------|----------|
| <路径> | <新增/修改/删除> | <一句话说明> |
```

## 关键约束

1. **事实导向**：所有内容（方案、改动、验证、文件清单）必须来自真实完成的开发工作和实际文件内容，不要臆测或夸大未实施的功能。
2. **引用准确**：文件路径统一使用 `file:///` 加绝对路径格式，代码片段需来自实际改动后的代码，关键位置可标注行号。
3. **不重复造文件**：写报告前先 `LS .lqs/update_report/` 确认是否已有同主题报告；若已有且为同一次更新则更新现有报告，否则新增序号。
4. **语言一致**：报告正文与用户沟通语言一致（默认中文）。
5. **区分 bug 修复与功能更新**：
   - 若本次工作以修复缺陷为主，使用 `bug_report` skill；
   - 若本次工作以新增功能、优化体验、清理重构为主，使用本 `update_report` skill。
6. **验证结果要诚实**：若仅完成静态验证（类型检查、语法检查、构建通过），需明确标注"静态验证通过，运行时待实测"，不要谎称已实测。

## 步骤

1. `LS` 查看 `.lqs/update_report/` 现有文件（若目录不存在则创建），确定下一个序号。
2. 用 `Get-Date -Format "yyyyMMdd_HHmmss"` 或 `Get-Date -Format "yyyyMMdd"` 取当前时间戳。
3. 回顾本次开发的对话历史/改动文件，梳理需求背景、方案、改动详情。
4. 按上述结构与命名规则，用 `Write` 创建报告文件。
5. 向用户确认文件已生成，给出文件路径链接，并简述序号/标题。
