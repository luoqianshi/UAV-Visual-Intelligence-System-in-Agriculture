## 一、系统功能介绍

「田间智瞰」是一套面向智慧农业场景的无人机（UAV）视觉智能监测平台，以甘蔗幼苗为首发作物对象，打通了 **数据管理 → 数据处理 → 数据集管理 → 算法广场** 的 AI 应用全链路闭环。

### 1.1 业务背景与痛点

大田作物苗期监测长期依赖人工下地抽样调查：效率低、覆盖面窄、主观误差大。无人机航拍可以低成本获取整块田的高分辨率影像，但原始影像存在三个工程难题：

- **图太大**：单张航拍图可达数千万像素，直接缩放送检会导致幼苗等小目标特征丢失；
- **光照不均**：田间逆光、阴影造成局部对比度差，影响模型召回；
- **目标密集**：幼苗成片分布，逐块检测后在分块边界处极易重复计数。

本系统的价值就是把「无人机图片 → 可信的田间出苗统计报告」这一流程产品化。

### 1.2 四大功能模块

| 模块 | 功能 |
|------|------|
| **数据管理** | 飞行架次登记（CRUD）、`data/` 目录启动自动扫描注册、图片分页浏览/懒加载/动态缩略图（400px）与中图预览（1920px）、元数据编辑、架次删除（仅删登记不删原始文件） |
| **数据处理** | 批量 CLAHE 图像增强 / 滑窗裁切异步任务，进度轮询、结果预览；加工数据自扫描重建、状态机管理（pending→processing→completed/failed/interrupted），单图失败隔离不影响整批 |
| **数据集管理** | COCO / YOLO / VOC 三种主流标注格式自动识别、数据集导入注册、统计报告（类别分布/图片尺寸/标注量）、图片浏览与删除 |
| **算法广场** | ① 算法管理：6 个 YOLO 甘蔗幼苗检测模型（YOLOv5su/v8s/11s/12s/12n/26s）统一注册、热切换激活、运行时动态注册新模型；② 作物检测：上传图片 → 同步推理 → 标注图 + 检测列表；③ 作物计数：高分辨率原图 → 异步流水线 → 总数/密度/面积/热力图/置信度分布/标注图 |

### 1.3 典型使用流程

无人机降落 → 拷贝架次图片到 `data/`（系统自动扫描注册）→ 数据处理模块做 CLAHE 增强或滑窗裁切 → 数据集模块构建训练集 → 算法广场选定模型 → 对高分辨率原图发起异步计数 → 前端轮询进度 → 获得带热力图和置信度分析的计数报告。

## 二、技术架构与核心技术方案

### 2.1 总体架构

```
┌────────────────────────────────────────────────┐
│  Vue 3 + Vite + Pinia + Tailwind + ECharts     │  SPA 前端（17 条路由）
│  axios 统一封装 · 构建产物直出 backend/static   │
└──────────────┬─────────────────────────────────┘
               │ /api/*  统一响应信封 {success,data,message}
┌──────────────▼─────────────────────────────────┐
│  Flask 2.2.3（Blueprint 路由 + SPA 静态托管）    │
├─────────────────────────────────────────────────┤
│  API 层   health / models / detect / counting   │
│           batches / processing / datasets       │
├─────────────────────────────────────────────────┤
│  核心引擎层（core/，纯 Python 可独立测试）         │
│  DetectionEngine   原子化单图 YOLO 推理           │
│  CountingEngine    高分辨图计数编排流水线          │
│  ModelRegistry     模型注册中心（YAML+LRU+热切换）│
│  BatchRegistry     架次注册中心（自动扫描+索引）   │
│  ProcessingEngine  批量增强/裁切执行器            │
│  DatasetRegistry   数据集注册（COCO/YOLO/VOC）    │
│  TaskManager       异步任务队列（线程池）          │
├─────────────────────────────────────────────────┤
│  算法工具层  clahe.py / tiling.py / nms.py       │
├─────────────────────────────────────────────────┤
│  存储层   YAML 注册表 + 文件系统（data/output/）  │
└─────────────────────────────────────────────────┘
```

**架构决策要点**：引擎层与 Web 层完全解耦——所有核心类（检测、计数、注册中心）不依赖 Flask，可脱离 HTTP 独立实例化和单元测试，全项目 103 项 pytest 用例（核心引擎 TDD + API 接线测试）。

### 2.2 核心技术方案一：高分辨率图像计数流水线（CountingEngine）

这是系统最有技术含量的部分，解决「大图 + 小目标 + 密集计数」问题。完整流水线：

```
高分辨率原图
  → ① CLAHE 增强（可选，默认关闭）
  → ② 滑窗分块（tile_size=640，overlap=5%，边缘回退补齐）
  → ③ 批量分块推理（batch predict，失败自动回退逐块串行）
  → ④ 局部坐标 → 全局坐标映射
  → ⑤ 全局置信度二次过滤（可选）→ 全局 NMS 去重（IoU=0.5）
  → ⑥ 统计输出：总数 / 密度(株/m²) / 面积 / 8×8 热力图 / 置信度三档分布
```

关键设计细节：

1. **分块策略**：步长 = `tile_size × (1 - overlap_ratio)`，5% 重叠带保证横跨边界的幼苗至少在一个块内完整出现；`calc_starts` 对边缘做回退，保证所有块尺寸一致（利于批量推理对齐）。
2. **全局 NMS 去重**：各块独立检测后，重叠区域的同一目标会被检出两次且坐标略有偏差。将所有检测框映射回全局坐标后，按置信度降序做贪心 NMS（同类别才抑制），从根本上去除重复计数。
3. **单块短路优化**：原图 ≤ tile_size 时自动跳过 CLAHE/全局过滤/NMS，避免无意义计算。
4. **截断风险监控**：逐块记录 `max_det_reached` 标记——某块检出数达到 max_det 上限即记日志并回传前端，提示密植截断风险，避免"静默少计"。
5. **内存直传不落盘**：子块图像全程驻留内存（numpy 切片零拷贝），批量送入 `predict`，避免磁盘 I/O 成为瓶颈；可选 `save_tiles` 调试模式落盘子块与局部标注。
6. **BGR 色彩通道纪律**：全链路保持 cv2 的 BGR 顺序直传 ultralytics，杜绝 RGB/BGR 反转导致的检测失准（注释中明确约定）。

### 2.3 核心技术方案二：模型注册中心（ModelRegistry）

- **YAML 声明式配置**：`config/models.yaml` 描述 6 个模型的权重路径、推理参数（imgsz/conf/iou/max_det）、类别名；
- **LRU 缓存引擎实例**：`OrderedDict` 实现，上限 3 个 YOLO 实例（单实例占显存/内存大，无限缓存会 OOM），命中时 `move_to_end`，超限时淘汰最久未用；
- **热切换**：`switch()` 先预加载目标引擎（提前暴露权重缺失等错误）再改激活指针，切换失败不影响当前服务；
- **动态注册**：API 上传新模型 → 权重文件落盘 → 配置追加并**持久化回 YAML**（自定义 representer 保持字段顺序与内联列表格式），重启后不丢失；
- **懒加载**：引擎实例按需创建，避免启动期强依赖 ultralytics——未装 torch 时系统降级运行，模型管理/数据管理照常可用，推理 API 返回明确降级提示。

### 2.4 核心技术方案三：推理稳定性设计（DetectionEngine）

- **参数三级优先级**：请求参数 > 模型 YAML 配置 > 引擎内置默认值；
- **GPU → CPU 自动降级**：识别 CUDA 相关异常（`cuda`/`device`/`gpu` 关键词）后自动改用 CPU 重试，应对 GPU 间歇性不可用；
- **device 归一化**：`'auto'`/`''`/`None` → `None`（ultralytics 自动选卡），`'cuda:0'` → `int 0`——规避了 ultralytics 8.4.60 中 `'auto'` 字符串直接抛 ValueError 的坑；
- **批量推理容错**：`detect_batch` 失败时由计数引擎兜底回退为逐块串行，保证任务整体不失败。

### 2.5 核心技术方案四：异步任务与状态管理

- **TaskManager**：`ThreadPoolExecutor(max_workers=1)` + 内存任务表，任务 ID 含时间戳+UUID；支持进度回调（`on_progress(phase, done, total)`），前端轮询 `/api/counting/tasks/{id}`；
- **为什么并发=1**：GPU 推理是显存密集型操作，串行化避免多任务争抢显存导致 OOM，同时保证计数结果的可复现性；处理类任务使用独立队列互不影响；
- **处理任务状态机**：YAML 持久化 + `output/` 目录自扫描重建（基于每个任务目录下的 `index.json` 快照），服务重启后任务记录与产物可恢复。

### 2.6 工程化亮点

| 方面 | 实践 |
|------|------|
| API 设计 | 统一响应信封 `{success, data, message}`；错误语义化（ValueError→400 / KeyError→404 / 依赖缺失→503 而非 500） |
| 部署 | `start.ps1` 一键脚本：环境检查 → 依赖安装 → 前端构建 → Flask 单端口（:5000）同时服务 API 与 SPA |
| 测试 | 103 项 pytest：核心引擎 TDD（patch 掉 ultralytics 依赖）+ API 接线 + 端到端处理集成 |
| 容错 | 单图失败隔离、任务级 try/catch、降级提示而非崩溃 |

## 三、面试深挖问题与参考回答

### Q1：无人机图这么大，为什么不直接 resize 到 640×640 送模型？分块带来了什么收益和问题？

**答**：甘蔗幼苗在航拍图中可能只占 20×20 像素。以 5000×4000 原图直接缩到 640×640 为例，目标被压缩到约 2.5×2.5 像素，特征几乎完全丢失，召回率会崩。滑窗分块保持了目标的原始尺度。
代价有两个：一是**边界目标被切开**——用 5% 重叠带缓解，保证边界目标在某个块内完整；二是**重叠区重复计数**——用全局 NMS 解决：所有块检测结果映射回全局坐标后，按置信度降序贪心抑制 IoU>0.5 的同类别框。这两个手段配合使用，计数偏差可控制在业务可接受范围。

### Q2：全局 NMS 的阈值怎么定的？和模型内部 NMS 是什么关系？

**答**：系统里有两级 NMS。模型内部 NMS（iou=0.7）在逐块推理时由 ultralytics 执行，去掉单块内的冗余框；全局 NMS（iou=0.5）在坐标映射后执行，专门处理跨块重复。全局阈值设得**更低**（更激进），因为跨块的同一目标经过两次独立推理，框的位置偏差比单块内重复框更大，需要更低的 IoU 阈值才能匹配上。两个阈值解耦、可在计数参数里独立调节。

### Q3：模型热切换怎么做的？并发请求打到一半切换会发生什么？

**答**：`ModelRegistry.switch()` 分两步：先 `get_engine(name)` 预加载目标引擎到 LRU 缓存（权重缺失等错误在这一步暴露，切换失败当前服务不受影响），成功后再改 `_active_model` 指针。Python 中字典/引用的读写在 GIL 下是原子的，所以"读到旧模型还是新模型"只影响单个请求用哪个版本，不会出现读到半初始化状态。正在执行的任务持有的是引擎实例引用，不受指针切换影响。真正的风险点是 LRU 淘汰：如果缓存满了（3 个），最久未用的引擎会被回收，下次用到要重新加载——这是显存占用和加载延迟的权衡，上限做成可配置。

### Q4：为什么异步任务用 ThreadPoolExecutor 且并发=1，而不用 Celery + Redis 这类方案？

**答**：三个原因。第一，**资源约束**：瓶颈在 GPU 显存，并发推理只会 OOM，串行执行吞吐并不会更差；第二，**部署形态**：这是单机部署的田间工作站场景，引入 Redis + Celery 等于让农业现场运维两个额外中间件，成本远大于收益；第三，**够用就好**：ThreadPoolExecutor + 内存任务表 + 进度回调已经覆盖了"提交-轮询-取结果"的完整交互。
如果未来要上多机集群，我会把 TaskManager 抽象成接口，底层换成 Celery/RQ，API 契约不变——这正是把任务管理收敛成独立类的原因。

### Q5：CLAHE 增强为什么默认是关闭的？开了会有什么问题？

**答**：这是一个**训练-推理分布一致性**问题。我们的模型训练时没有使用 CLAHE 增强，推理时如果开启，输入分布发生偏移（局部对比度被强行拉升），反而会降低精度。所以引擎默认关闭，只在逆光/阴影严重的架次由用户显式开启。这个默认值是通过实验对比确认的，也写进了 README 的参数对齐清单。这给我的启示是：**预处理不是越多越好，必须和训练管线对齐**。

### Q6：GPU 推理失败了怎么办？你的降级策略会不会掩盖真正的 bug？

**答**：检测引擎捕获异常后先用关键词匹配（cuda/device/gpu）判断是不是 CUDA 不可用类错误，是则降级 CPU 重试并记 warning 日志；其他异常（比如输入图像损坏）直接上抛。为了避免掩盖 bug，有两个保护：一是降级必记日志，可审计；二是 503 语义——如果是依赖缺失（torch 没装），API 返回 503 明确提示降级，而不是 500 混淆视听。当然关键词匹配是启发式的，更严谨的做法是匹配 ultralytics 的异常类型，这是可以改进的点。

### Q7：YAML 做持久化，为什么不直接上 SQLite/MySQL？

**答**：当前数据规模是几十架次、几千张图的元数据，YAML 的可读性、可手工修复性、零依赖是优势；而且我们做了**文件系统即真相源**的设计：`data/`、`output/` 目录本身就是数据，YAML 只是索引，启动时自动扫描重建，即使 YAML 损坏也能从目录结构恢复。代价是并发写入和复杂查询能力弱。如果接入企业级多用户场景，我会换成 SQLite（仍保持单文件部署）或 PostgreSQL，注册中心的接口已经收敛，替换成本低。

### Q8：计数结果的可信度怎么保证？业务方凭什么信这个数字？

**答**：四个机制。第一，**截断监控**：某块检出数触顶 max_det 时打标回传，提示"此处可能密植少计"；第二，**置信度分布**：报告给出 high(≥0.7)/mid(≥0.4)/low 三档分布，业务方可按高置信度子集折算；第三，**热力图**：8×8 网格密度分布可与人眼抽查比对，异常区块一眼可见；第四，**可复现**：每次计数的参数快照（params_snapshot）随结果持久化，同图同参结果可复现。最终数字会结合作物行距、品种等农学先验由农技人员校准。

### Q9：密度（株/m²）是怎么算的？地面分辨率 0.85 cm/px 哪来的？

**答**：面积 = 图像宽 × 高 × (ground_resolution/100)²。0.85 cm/px 是地面采样距离（GSD），由飞行参数决定：GSD = 飞行高度 × 传感器像元尺寸 / 焦距，这个值随架次元数据登记（我们有 5m/8m/10m 三种航高架次）。目前作为计数参数传入，后续规划是从架次元数据自动带出，减少人工填参错误。

### Q10：如果让你把这个系统部署到华为云/边缘设备上服务多个农场，架构要怎么改？

**答**：分三层改。**接入层**：Flask 换 FastAPI（原生异步+OpenAPI 文档），前置 Nginx 做负载均衡；**计算层**：推理服务独立成 gRPC/HTTP 微服务，模型用 TensorRT 或昇腾 CANN 做推理加速，配合 KServe/Triton 做模型版本管理和自动扩缩容——华为场景下优先适配昇腾 NPU；**任务层**：TaskManager 换成消息队列（Kafka/RocketMQ）+ Worker 池。边缘侧（农场本地）保留轻量版做实时性要求高的计数，云端做模型训练、版本下发和多租户数据管理。核心引擎层因为不依赖 Flask，可以原样复用到新架构里——这就是当初坚持引擎与 Web 解耦的回报。

### Q11：103 项测试都测什么？AI 系统的测试和普通后端有什么不同？

**答**：分三层：**核心引擎层**用 TDD，patch 掉 ultralytics（构造假 YOLO result 对象），验证坐标映射、NMS、统计、状态机等纯逻辑；**API 层**测路由接线、参数校验、错误码语义；**集成层**跑端到端处理流程。AI 系统测试的特殊性在于：模型输出是**概率性**的，不能断言"检出 5 株"，所以测试重点是**编排逻辑的正确性**（坐标对不对、去重对不对、降级路径走没走），模型精度则用独立的离线评估集把关，不进单元测试。

### Q12：项目中遇到过最难的 bug 是什么？

**答**：ultralytics 的 device 参数坑。传 `'auto'` 字符串在 8.4.60 版本里 `select_device` 直接抛 ValueError，传 `'cuda:0'` 字符串也不被接受（期望 int 0）。排查时发现不同版本行为还不一样。最后的解法是写了一个 `_normalize_device` 归一化函数：`'auto'/''/None → None`（让 ultralytics 自己选卡）、`'cuda:N' → int N`、纯数字字符串转 int，并补上单元测试锁定行为。这类第三方库的版本行为差异，靠文档是查不全的，必须用测试把适配层钉死。

## 四、简历用项目介绍（一段话版）

> **田间智瞰 · 无人机农作物智能监测系统** | Python / Flask / Vue3 / YOLO / OpenCV
> 独立设计并落地的智慧农业 AI 应用平台，覆盖数据管理、图像处理、数据集管理与模型推理全链路。针对无人机高分辨率影像的小目标计数难题，实现「CLAHE 增强 → 滑窗分块 → 批量推理 → 坐标映射 → 全局 NMS 去重」计数流水线，输出总数/密度/热力图/置信度分布一体化报告；设计 YAML + LRU 缓存的模型注册中心，支持 6 个 YOLO 模型热切换与运行时动态注册；基于线程池实现异步任务队列与 GPU→CPU 自动降级，保障推理服务稳定性。系统采用引擎层与 Web 层解耦架构，配套 103 项 pytest 测试（TDD），支持单端口一键部署。

### 简历要点提炼（可拆分为 bullet）

- 针对高分辨率航拍图小目标漏检问题，设计滑窗分块 + 全局 NMS 去重的计数流水线，解决边界目标重复计数；
- 实现基于 LRU 缓存的模型注册中心，支持多模型热切换、动态注册与 YAML 持久化；
- 设计 GPU→CPU 推理自动降级与批量推理失败回退机制，提升服务可用性；
- 引擎层与 Web 框架解耦设计，103 项单元/集成测试覆盖核心逻辑；
- 全栈交付：Flask RESTful API + Vue3 SPA，一键脚本单端口部署。
